产品计划书 · 精简版

把分散攻略，
变成可执行的自驾行程。

路书 Waymark 面向自驾旅行组织者：按偏好生成逐日计划，用真实来源核对，方便同行者一起调整。

最终交付：一份保存在 App 里的可编辑行程，包含互动路线地图、每日安排和来源；确认后可分享链接或导出 PDF。

用户痛点

查资料、算车程、找住宿分散在多处

核心做法

安排、依据、替代项放在同一天

首发假设

美国西部自驾，先试一条路线

工作名：路书 Waymark产品假设待试点验证
01 / 用户问题

用户要的不是更多攻略，
而是少做重复核对。

01
每天是否排得合理？

车程、停留时间和景点顺序要自己反复估算。

02
不喜欢这个活动怎么办？

替代项要符合兴趣、时间和当天路线。

03
附近住哪里、选择多不多？

住宿与路线分开查，晚发现问题就得重排。

04
天气变化后怎么调整？

改一个点会影响车程、住宿和后续安排。

产品目标：让用户在同一份行程里核实、比较、确认和调整。
问题来自用户描述，仍需访谈验证
02 / 核心流程

从旅行条件，到同行确认。

01输入条件

日期、人数、必去点、兴趣、预算和每日驾驶上限。

02生成逐日草案

按地理顺序排地点与住宿区域，标出估算和待确认项。

03审核与替换

对比活动、车程、体力、时间和来源。

04预览影响

检查住宿与后续日程，再由用户确认更新。

05分享并出发

同行者查看确认版；途中按天气或实际情况重排。

首版必做

逐日编辑、地图与驾驶估算、来源卡、活动替代、住宿区域联动、同行确认。

明确不做

不做导航、酒店交易、实时库存承诺或无授权的社交平台批量抓取。

用户确认每个关键安排，AI 不替用户拍板
03 / App 信息架构

四个主入口，承载一次旅行的完整周期。

用户从行程进入规划和执行；发现、收藏提供可追溯的内容入口；个人设置保存偏好与同行协作。

主入口页面层级用户完成的事
行程行程列表 → 行程总览 → 每日详情 → 编辑/替换 → 影响预览创建旅行、看地图和每日安排、调整路线/活动/住宿、确认并执行。
发现目的地/主题 → 游记或旅行社方案 → 来源详情按地点和偏好浏览公开攻略或已收录方案，查看原始出处后保存到某天。
收藏收藏夹 → 地点/活动/行程资料 → 添加到旅行整理已保存内容，保留链接、适用季节和个人备注，复用到新行程。
我的旅行偏好 → 同行成员 → 通知/离线/隐私设置设置预算、驾驶和体力偏好；管理成员权限、下载行程和资料来源。
行程内工具地图/列表切换、日期导航、筛选、路线段详情、天气与提醒。
协作入口按天评论、候选投票、负责人确认；修改保留操作者和时间。
全局状态草案、待核实、待同行确认、已确认、已变更；来源显示更新时间。
导航原则：发现和收藏服务于行程；所有被采用的地点与建议，最终都落到具体日期、路线和来源上。

04 / 页面布局与操作

每个关键页面，都要回答一个明确问题。

页面页面主要区域关键操作 / 结果
行程首页即将出发/进行中行程；待确认事项；继续上次编辑；创建入口。新建旅行、回到待处理日期、打开已分享行程。
创建行程日期与天数、起终点、同行人数/车型、必去点、兴趣、预算、驾驶/体力上限。检查缺失条件；生成可编辑草案；明确列出采用的假设。
行程总览顶部日期和路线摘要；互动地图；逐日卡片；日里程/驾驶时间；住宿摘要；冲突提示。切换地图/列表；进入某天；邀请同行；分享确认版。
每日详情日期与起终点；地图和路线段；按时间排列的停靠/活动；时长与强度；来源；过夜区域。加点、删点、拖动排序、替换活动、查看来源、编辑住宿。
替代选项按兴趣、体力、耗时、季节/开放情况筛选；候选卡片含路线绕行、停留时间、适用原因和来源。打开原始资料；并列比较；收藏；选择一项进入影响预览。
影响预览变更前后对照：新增车程/时长、当天活动、到店时间、住宿位置、次日路线和警告。确认应用、返回比较或撤销；写入修改记录并更新行程状态。
住宿规划过夜区域地图与候选列表；到当天终点/次日首站距离；预算、日期、预订入口及信息更新时间。先选住宿区域，再打开合作/外部预订；房价房态无授权时明确显示“外部查询”。
来源 / 执行 / 分享来源原文链接、作者/机构、旅行日期、摘录与更新时间；执行页突出今天和导航；分享页提供确认版本。核验并标记来源；跳转地图导航；记录现场调整；分享只读链接或导出 PDF。

关键页面共用规则：建议卡同时呈现“为什么适合你、依据在哪里、会影响什么”；事实、旅行者体验和系统估算分开展示。

布局描述到页面区域和关键操作，不限定视觉风格
05 / 核心流程、状态与数据对象

计划可追溯，变化有预览，确认可回退。

A · 从需求到确认行程

建旅行 → 填日期/偏好/必去点 → 生成草案 → 检查车程、时间和过夜区域 → 逐日查看来源与选项 → 同行评论/投票 → 负责人确认 → 分享。

B · 替换一个活动

选当天活动 → 查看匹配选项与出处 → 对比体力/时长/绕行 → 看当日、住宿和次日影响 → 应用或放弃 → 留下变更记录；来源过期时先提示复核。

C · 住宿与路线联动

查看过夜区域 → 比较与终点/次日首站的距离 → 选择区域或外部候选 → 回看当天到达时间与次日出发负担 → 确认后关联该日期。

D · 旅行中临时调整

天气/封路/延误或用户手动提出变化 → 只重算受影响的未执行部分 → 展示可行替代与影响 → 用户确认/手动改 → 保存新版本；无网时打开已下载的确认版。

核心对象记录内容产品用途
Trip / Day日期、同行者、偏好与限制；每日起终点、状态和确认版本。承载行程框架和逐日审核。
Stop / Route leg地点/活动、顺序、停留时长、距离/时间估算、导航目的地。重排或替换时重新计算路段和日负担。
Lodging plan过夜区域、候选链接、日期、与路线的关系；价格/房态来源与时间。把住宿纳入当天和次日检查；区分区域建议与实时库存。
Evidence / Change原始链接、来源类型、作者/机构、适用日期、摘录/更新时间；变更前后值、操作者、时间。支持核实、归因、回看和撤销；体验建议不冒充官方事实。
状态流转：草案 → 待核实 → 待同行确认 → 已确认 → 已变更。每项来源和实时信息另标“有效/需复核/不可用”；无依据时不生成事实结论。
适用于规划、协作和旅行中调整

05 / 数据从哪里来

首版能靠公开资料启动；
两类数据需要商业接入。

要解决的问题来源 / 首版做法可行性与限制
景点、开放、园区提醒美国国家公园 NPS API；各园区官网可申请 API key；按地区接入，逐个补齐州/地方来源。
天气与预警美国 NWS API开放预报和警报接口；需遵守请求规范，展示来源与更新时间。
地图、距离、车程Google Maps Routes API 或其他地图服务有路线/距离能力；需核算计费、密钥和地图展示许可，时间仅为估算。
游记、旅行社行程用户粘贴小红书 / Instagram 等链接、上传旅行社行程；编辑人工精选；查看小红书开放平台文档可先做小规模试点；注明原链接与旅行日期，不承诺全网搜帖或批量抓取。
住宿候选、价格、房态首版显示住宿区域和预订跳转；后续谈 OTA实时库存依赖合作权限；Booking.com Demand API需管理联盟合作伙伴资格与账号权限。
可行性判断：行程规划、官方信息、用户提供的攻略链接可先做；地图 API 是成本与许可评估项；社交平台批量内容和实时酒店库存不是首版前提。
资料只支持它能证明的内容：体验不等于官方事实
06 / 首版范围与依赖

先证明一条路线真的更好规划。

首版做

一个地区，一条完整规划闭环

创建旅行 → 逐日草案 → 来源核对 → 替代活动 → 地图/住宿联动 → 同行确认 → 分享和 PDF。

首版不做

不依赖尚未拿到的数据权限

不做跨平台帖子库、酒店预订交易、实时房态保证或全美路线覆盖。

低风险可启动用户输入/上传、公开链接、NPS 与 NWS 资料。
需采购与评估路线/地图 API 计费、许可、区域覆盖和精度。
需合作或授权社交平台规模化内容、住宿实时库存与报价。

判断门槛：先用人工精选资料和一条示范路线验证流程；拿到用户价值证据后，再谈平台和酒店数据合作。

首发路线及供应商待验证
07 / 怎么判断值得做

先用真实行程验证三个问题。

省时间了吗？记录规划耗时和外部搜索/切换次数。
行程可执行吗？统计每日确认率和发现的车程/住宿冲突。
来源足够可信？记录来源核对率，以及用户拒绝建议的原因。
1

访谈与路线选择

找近期自驾组织者，选一个示范路线和脱敏行程。

2

做可点击原型

验证逐日查看、替代、住宿联动和分享。

3

核算数据成本

测地图 API；确认官方数据覆盖；询问内容与住宿合作门槛。

先做决定：首发用户是谁、试点路线选哪条、地图服务的成本是否可接受。
商业模式和扩区等价值验证后再定
