产品计划书 · v0.2

让每一天的
旅行安排都有依据。

路书帮助自驾旅行者，把自己的偏好、真实旅行体验、旅行社路线、官方信息和地图住宿资料，整理成一份可核对、可替换、可同行共识的行程。

核心承诺：AI 可以帮你规划，但每条关键安排都能看见来源、适用条件和仍待确认的事项。

给谁

自己做主的自驾旅行者

尤其是第一次去陌生地区、路线跨城、同行偏好不同的人。

解决什么

规划和核实行程太分散

不用在攻略、地图、酒店和聊天记录之间来回拼信息。

怎么做到

安排、证据和决策放在一起

按天审核，能比较替代项，修改后能看见路线和住宿的连带影响。

路线规划证据可追溯逐日共创途中可调整

01 / 用户痛点

现在的规划像一场
没有工作台的研究项目。

信息并不缺，缺的是把它们组织成一个可判断、可修改、能协同行动的计划。

01
AI 行程看起来完整，用户仍得逐点查证

不知道每日安排是否合理；行驶距离、停留时长、景点价值和个人兴趣都要自己复核。

02
替代方案缺少依据，选择成本高

不想徒步时，很难快速找到同区域、同一天可执行的轻松选项，还要确认它是否真实存在。

03
住宿搜索和行程规划脱节

先排路线，再另开地图和订房平台找酒店；住宿稀缺或位置不合适时，路线又得重排。

04
做好的计划不适合途中调整

天气或体力变化后，改一个点会牵动驾驶、后续安排和住宿，却没有清晰的影响说明。

用户真正想买到的结果：不是更多攻略，而是少做重复搜索，知道为什么这样安排，并能安心地做取舍。
问题定义来自用户描述，待访谈验证02 / 11
02 / 目标用户与使用场景

先服务需要自己做功课的
多人自驾小团体。

核心用户

行程组织者 / 旅行发起人

负责搜资料、定路线、协调同伴，担心遗漏关键事项，也不想替 AI 的建议背书。

共同决策者

同行家人或朋友

对体力、兴趣、驾驶时长和预算有不同偏好，希望能直接对具体一天表达意见。

关键使用场景

出发前 · 从零搭路线给出人数、天数、必去点和偏好，先得到可讨论的路线框架。
出发前 · 逐日确认核对每天去哪、开多久、做什么、住哪里，替换不合适的安排。
旅行中 · 临时改计划遇到天气或现实变化，查看可行替代项和被影响的后续安排。

首发切口建议：美国西部自驾路线。它能集中验证长距离驾驶、国家公园活动、住宿稀缺、季节和天气变化等复杂问题；首版先支持一个示范走廊，不追求覆盖所有目的地。

首发地区是产品假设，需通过用户验证确定03 / 11
03 / 产品解决方案

围绕“每日计划”组织
信息和共同决策。

用户先定旅行约束，系统给出可审核的日程；每个安排附依据，每次修改都说明会影响什么。

STEP 01输入旅行条件

同行人数、日期、必去点、兴趣、体力、驾驶上限和预算倾向。

STEP 02生成路线草案

按地理顺序与停留节奏编排天数，标出假设和待确认信息。

STEP 03逐日看证据

对照游记、旅行社路线、官方资料和地图数据，判断来源适用性。

STEP 04比较并替换

查看不同活动的时间、体力、绕行和住宿影响；同行者可共同确认。

STEP 05带着计划上路

保留确认版；临时调整时重算相关安排并留下变更记录。

示例 · 优胜美地这一天

计划：山谷观景 + 徒步路线。偏好不符：用户不想徒步。可选：低体力观景组合；展示多走/少走的时间差、停车/开放信息和可追溯来源。选中后重新评估当晚住宿和次日出发。

产品反馈闭环

用户接受、替换或标记“不感兴趣”的结果，都能帮助调整本次行程；只有用户明确同意，偏好才保存为未来旅行设置。

日程是用户审核的草案，不是自动替用户做决定04 / 11

06 / 资料来源与信任机制

不同来源回答不同问题，
不把“有帖子”当成“已证实”。

资料类型能提供的价值不能直接证明产品如何使用
个人旅行帖子 / 游记体验、偏好、实际停留感受、踩坑和活动细节。当前开放状态、未来天气、每个人都适合。引用原帖链接和旅行时间；提炼可核实事实与主观感受，分开显示。
旅行社执行过的行程常见路线组合、每日分段、住宿城市、成熟线路参考。适合自驾、自由活动时间充足、每位团员都完整执行。标为团队/大巴/套餐背景；与自驾路况和个人偏好重新计算。
官方来源开放时间、预约、道路关闭、规则与安全信息。用户是否喜欢、体验是否值得。优先验证高影响事实，显示来源机构与最近核验时间。
地图 / 住宿服务路线距离、估算车程、地点位置、住宿候选和供应情况。固定驾驶时间、实际库存不变、酒店适合所有人。标明数据来源与更新时间；临近出发再次确认。

每条建议给出“证据卡”

来源名称与类型 · 原始链接 · 内容日期/旅行日期 · 支持的具体判断 · 与本次行程的适配度 · 尚未核实项。

来源接入分阶段

首版支持用户粘贴公开链接、上传自有行程文件和人工精选资料；批量平台数据只在官方接口、授权或合作允许后接入。公开可见不等于默认可批量抓取。

关键原则：观点与事实分层；来源越重要，核验门槛越高06 / 11
07 / 首版范围与产品边界

先验证“规划工作台”
是否真的省力。

首版包含

围绕行程决策的最小闭环

创建自驾旅行 → 生成逐日草案 → 查看来源 → 比较/替换活动 → 看路线和住宿联动 → 同行确认 → 保存分享。以手机 App 为主，先支持单一示范区域。

首版不做

不把范围扩成旅行超级 App

不做机酒交易/支付；不替代 Google Maps 或 Apple 地图导航；不保证酒店库存；不自动批量抓取受限制的社交平台；不承诺没有来源的“真实体验”；不做泛化全球路线覆盖。

关键依赖和降级方案

路线与车程依赖地图服务可用性和许可；不可用时展示用户可核验的路线链接，不伪装成精确导航。
住宿供应首版可从住宿区域和公开候选开始；实时价格/房态交给合作 API 或跳转预订方核实。
社交内容链接导入与人工策展先行；平台授权/API 或正式合作是规模化自动接入的前提。
首版目标：验证核心工作流，不提前承诺未拿到的接口能力07 / 11
08 / 核心体验与规则

替换一个点，系统要解释
会连带改变什么。

一天的计划卡至少包括

日期与起终点 · 预计驾驶段/时间 · 当日主要体验 · 活动体力/时长标签 · 住宿区域 · 来源入口 · 用户确认状态。

替代项的比较维度

为什么匹配 · 与原安排的车程差 · 所需时间与体力 · 是否需要预约 · 对当晚住宿/次日出发的影响 · 证据来源。

替换后影响预览

明确指出增加/减少的驾驶、可能压缩的停留、住宿地点是否改变、次日是否需要重排；用户确认后再应用。

信息状态要能区分

已由官方核实、来自旅行者/旅行社经验、地图估算、待用户确认分别呈现，并显示更新时间。

失败处理：资料不足时可以给出“需要补充信息”的问题或不推荐替换；不为了让行程看起来完整而编造来源、路线精度、酒店库存或开放状态。

关键交互判断：用户能否在一个页面内做决定并理解后果08 / 11
09 / 商业模式假设

先验证价值，再决定
怎样收费。

当前没有足够证据支持具体定价或市场规模。以下是待验证的商业路径，不是已确定结论。

假设 A

单次旅行 / 高级计划

基础路线草案免费；深度证据整理、多人协作、复杂多日重排作为付费能力测试。

假设 B

按旅行季订阅

频繁自驾或持续规划多次旅行的用户，可能更愿意为长期资料管理和跨行程偏好付费。

假设 C

透明的预订合作

用户主动跳转后产生的住宿/活动合作收入可探索；商业推荐要标识，并与行程匹配排序隔离。

需要访谈验证：用户愿意为节省规划时间、来源核查和多人协作中的哪一项付费？他们现在已有的 AI、地图和预订工具是否已经足够？
不在验证前写入收入预测或付费转化假设09 / 11
10 / 验证计划与成功指标

先验证工作流是否减负，
再扩大资料和地图投入。

第一轮：问题访谈

找近期规划过多日自驾旅行的人，复盘他们真实的搜索、核实、住宿选择、同行决策和途中改动；收集一份脱敏的实际行程作测试输入。

第二轮：可用性试走

让用户用一个真实路线完成创建、逐日审核、替换活动和选住宿；观察卡住点、跳出工具的次数，以及用户对来源的信任。

试点建议观察的指标（先记基线，不预设目标值）

规划效率从填写基本条件到第一版可讨论行程所需时间；每个计划外部搜索/切换次数。
计划可用度逐日确认率；日程被大幅重排的比例；驾驶/住宿冲突在出发前发现的数量。
证据价值来源卡打开率；用户判断“足以核实”的比例；因资料不适用被拒绝的建议。
目标值在首轮观察后设定
11 / 交付路线与待验证问题

从小范围真实行程开始，
逐步建立可信度。

阶段 0

定义与验证

访谈旅行组织者；选一个示范路线；确认数据来源、地图服务和住宿信息的可接入边界。

阶段 1

规划工作台原型

实现旅行约束、逐日行程、来源卡、活动替代、路线/住宿联动和分享评审。

阶段 2

小规模试点

用真实行程完成可用性测试；记录用户修改、来源缺口、规划时间和失败情况。

阶段 3

决定扩展方向

根据试点结果选择：更多路线地区、授权内容接入、协作能力、途中实时信息或商业验证。

优先验证的问题

首发用户和首发路线选谁？范围聚焦
第一版最先证明哪一个价值？价值排序
链接导入与人工策展能否支撑试点？资料策略
用户需要个人使用，还是多人协作？产品形态

近期目标：确认一个首发人群、一条真实试点路线、首版 3 个必做流程，以及需要验证的数据/服务合作问题。

产品假设需通过真实用户和路线验证
